## 1. 배경 [확정]

- 전시를 찾기 어려웠고, 찾은 전시의 얼리버드 기간이 이미 끝나 있던 경험이 계기
- 지금까지 네이버, NOL, 한가람미술관, 카카오톡 예약하기 등을 일일이 확인했음

## 2. 요구사항 [확정]

| 항목 | 내용 |
|---|---|
| 장르 순서 | 1순위 미술 전시, 2순위 뮤지컬, 이후 다른 장르도 추가 가능해야 함 |
| 메인 화면 | 캘린더가 바로 보임. 전시마다 시작일·종료일 표시. 필터 결과를 캘린더에 표시 |

| 수집 대상 변화 | 사이트 구조·정책이 계속 바뀌는 것을 전제로 설계 |

## 3. 기술 전제

- [확정] 프론트 React, 백엔드 Spring Boot, 인프라 AWS, DB PostgreSQL
- [확정] 모듈러 모놀리스, 처음에는 서버 1대. 나중에 MSA·Kafka·K8s로 확장 가능해야 함
- [확정] 크롤러는 "서버 1대에 같이 실행"과 "여러 대로 분리해 작업 분산" 중 선택 가능해야 함

- [확정] 모듈 경계를 강제하는 방법: Spring Modulith (2026-09-28 사용자 확인)

## 4. 설계 초안 요약 [안]

### 4.1 모듈

| 모듈 | 하는 일 |
|---|---|
| event-catalog | 전시·공연, 일정, 분류, 장소, 판매처 정보 저장·조회 |
| search | 캘린더 조회, 필터 처리 |
| collector | 수집 스케줄링, 크롤러 실행, 수집 결과 정규화 |
| source-adapters | 사이트별 수집 코드. 사이트 하나당 어댑터 하나 |
| classification | 분류 태깅 |
| web-api | React가 호출하는 REST API |
| admin | 관리자 API, 확인 대기 목록, 검수 모드 설정 |

- 모듈끼리는 공개 인터페이스와 이벤트로만 통신
- collector가 "수집 완료" 이벤트를 발행하면 event-catalog가 받아 저장. 처음에는 Spring 애플리케이션 이벤트 또는 DB 아웃박스, 나중에 Kafka로 교체

### 4.2 데이터 모델

- 장르는 테이블이 아니라 값(EXHIBITION, MUSICAL 등). 뮤지컬 추가 시 테이블 추가 없이 값만 늘림
- Event(제목, 장르, 장소, 설명, 대표 이미지 URL)
- EventPeriod(기간 종류: 실제 기간 / 얼리버드 1차 / 2차 …, 시작일, 종료일). Event와 1:N. 캘린더 두 탭은 기간 종류로 거름
- TicketOffer(판매처, 가격, 판매 기간, 예매 URL). Event와 1:N. 가격 필터·예매처 구분 기준
- Venue(이름, 주소, 시·도). 지역 필터는 시·도 기준
- Category(이름, 인기 여부, 표시 순서) + EventCategory(N:M)
- SourceRecord(출처, 원본 URL, 수집 시각, 원본 JSON/HTML, 해시). 파서를 고치면 사이트에 다시 요청하지 않고 원본으로 재처리
- 같은 전시 판별용: SourceLink(출처 고유 번호 → Event), MatchDecision(관리자 판정), VenueAlias(장소 별칭)
- 관리자용: ReviewItem(종류, 대상, 걸린 이유, 상태: 대기/승인/반려/자동 처리), AdminSetting(검수 모드, 기준값)
- 수집 결과는 바로 Event에 쓰지 않고 검수 단계를 거쳐 반영
- PostgreSQL daterange 타입과 인덱스로 월 단위 기간 겹침 조회

### 4.3 크롤러 실행 모드

- 설정 `collector.mode: embedded | distributed`
- embedded(처음): 서버 1대 안에서 스케줄러가 수집 작업을 만들고 같은 프로세스가 실행
- distributed(우선순위 낮음): 스케줄러는 작업 큐에 넣기만 하고, 크롤러 전용 인스턴스 여러 대가 꺼내 실행
  - 작업 큐는 PostgreSQL 테이블 + `SELECT ... FOR UPDATE SKIP LOCKED`, 나중에 Kafka로 교체 가능하게 인터페이스로 분리
  - 사이트별 요청 속도 제한은 인스턴스 합계 기준(DB 또는 Redis에 마지막 요청 시각 공유)
  - 스케줄 중복 실행 방지: ShedLock

### 4.4 확장 경로

1. 서버 1대, 모듈러 모놀리스, embedded 모드
2. 크롤러만 별도 인스턴스(같은 jar, 프로필만 다름)
3. 모듈 간 이벤트를 Kafka로
4. 필요한 모듈을 별도 서비스로 분리, K8s

- 다음 단계로 넘어가는 기준은 실제 필요. 예: 한 번 수집 시간이 수집 주기보다 길어지면 2단계

### 4.5 AWS 배포

- React 빌드 → S3(비공개, OAC) + CloudFront. 백엔드 EC2 1대
- CloudFront 경로 분리: `/api/*` → 백엔드(캐시 끔), 나머지 → S3. 같은 도메인이라 CORS·쿠키 문제 없음
- React Router 새로고침: CloudFront 오류 응답 403·404 → `/index.html`(200)
- 인증서: ACM us-east-1
- [확인 필요] DB 위치: EC2에 직접 설치 / RDS

### 4.6 관리자 화면

- [확정] 검수 모드 두 가지, 기본값 "이상한 것만 물어보기"
- [안] 모드를 바꿔도 이미 반영된 데이터는 그대로, 바꾼 뒤 들어오는 건부터 적용
- [안] "이상한 것" 기준 예시
  - 같은 전시 판별 점수가 애매함, 제목은 같은데 장소·도시가 다름, 관리자가 "다름"으로 판정한 쌍이 다시 합쳐질 상황
  - 종료일이 시작일보다 앞, 시작일이 너무 오래됨(NOL `10.01.20` 시작 상시 행사), 얼리버드 판매 기간이 전시 종료일보다 뒤, 예매처끼리 기간이 다름, 얼리버드 종료일이 "종료일 없음" 값(카카오 `2999-12-31`)
  - 가격 문장에서 숫자를 못 뽑음, 얼리버드가 정상가보다 비쌈, 예매처끼리 같은 차수 가격이 다름
  - 이미지 글자 인식 신뢰도 낮음, 이미지 값과 페이지 글 값이 다름
  - 어떤 분류에도 안 걸림, 미술 전시가 아닐 가능성(축제, 박람회, 입장권)
  - 검색 API로 발견했지만 기존 전시와 연결되지 않은 새 전시 후보
- [안] 화면: 대시보드, 확인 대기 목록(종류별 탭, "왜 걸렸는지" 한 줄), 같은 전시 판별(나란히 비교, 합치기/나누기, 되돌리기), 전시 편집·직접 입력, 새 전시 후보, 분류 관리, 출처 관리, 자동 처리 기록, 설정

## 5. 데이터 수집 핵심 [안]

### 5.1 수집 방식 우선순위

1. 공공 Open API
2. 사이트가 내부적으로 호출하는 JSON 요청
3. 서버가 내려주는 HTML 파싱(Jsoup)
4. 헤드리스 브라우저(Playwright for Java)

- 아래로 갈수록 화면 변경에 깨지기 쉽고 상대 서버 부담이 큼

### 5.2 사이트가 바뀌는 것에 대비

- 사이트별 수집 코드를 어댑터 하나로 격리
- 어댑터마다 조사 문서(조사 날짜, 확인 URL, robots.txt 내용, 필드 대응표)
- 원본(SourceRecord) 저장 → 파서 수정 시 원본으로 재처리. 저장한 원본 샘플로 파서 테스트, 실제 사이트는 하루 1회 가벼운 확인
- 수집 건수 급감이나 필수 항목(제목, 기간) 파싱 실패 증가 시 알림
- robots.txt·약관 페이지 해시를 주기적으로 비교, 바뀌면 알림
- 자동 수집이 막힌 사이트는 관리자 수동 입력으로 대체
- [확인 필요] 어댑터별 재조사 주기(초안: 분기마다)

### 5.4 크롤러 규칙

- 사이트당 최소 수 초 간격, 동시 요청 1개부터
- User-Agent에 서비스 이름과 연락처
- robots.txt·약관 금지 경로 제외. 로그인 필요 정보, 캡차·봇 확인 우회가 필요한 정보는 수집 안 함
- 하루 1회 [확정], 상세는 변경 감지된 건만 다시 요청(목록 해시 또는 `UPDATE_DATE_TIME` 비교). sitemap 우선 활용
- 원본 먼저 저장, 파싱은 따로
- 어댑터 인터페이스 초안: `sourceId()`, `fetchListing(ListingQuery)`, `fetchDetail(ListingItem)`, `parse(RawDetail)`

### 5.5 법적 유의 (법률 자문 아님)

- 근거: 대법원 2022. 5. 12. 선고 2021도1533 (야놀자 v. 여기어때, 무죄). 판단 근거가 곧 주의점
- 보호 조치 우회, 약관 동의한 회원 계정으로 수집하는 것은 위험
- 전체 복제 대신 캘린더에 필요한 최소 항목(제목, 기간, 장소, 가격, 예매 URL)만 저장, 상세는 원본 링크로
- 요청 속도를 낮게 유지. 이미지·소개글은 복제 게시 안 함
- 공개 서비스로 운영하기 전 사이트별 약관 재확인

### 5.6 얼리버드

- 핵심 데이터(사용자 문제를 해결하는 부분). 차수(1차, 2차, "슈퍼 얼리버드" 등)와 기간을 EventPeriod로, 예매처별 가격·기간은 TicketOffer별로
- NOL: 공지 텍스트(전체 차수) ↔ 가격 팝업(현재 차수) 대조. 카카오: 얼리버드 여부·할인율만, 종료일 없음
- 텍스트에 없으면 이미지에서 읽음. 자동으로 어려운 것(SNS 공지 등)은 관리자 직접 입력

### 5.7 분류 태깅

- 출처 분류는 "전시/행사", "전시/미술" 수준까지만 있음 → 직접 붙여야 함
- 1단계 미술 아닌 행사 거르기 → 2단계 키워드 규칙 → 3단계 관리자 수동 지정 → (선택) LLM 후보
- 사조와 전시 형태가 섞여 있으므로 한 전시가 여러 분류에 속하도록 N:M
- 분류 추천안: 세 묶음(무엇을 다루나 / 어떤 매체 / 어떤 형태). 첫 화면 기본 선택 추천: 인상주의·후기인상주의, 사진, 일러스트·원화·애니메이션 (표본 50여 건 기준)
- 키워드 예: 인상주의·후기인상주의 ← 인상주의, 인상파, 모네, 르누아르, 드가, 세잔, 고흐, 고갱, 로트렉 / 개인전 ← 개인전, solo exhibition / 비엔날레·아트페어 ← 비엔날레, 아트페어, 트리엔날레

### 5.8 이미지 속 텍스트

- 텍스트에서 먼저 찾고, 없을 때만 이미지 읽기
- 세로로 긴 이미지(실측 840×26420px)는 조금씩 겹치게 잘라서 인식
- [확인 필요] 방법: OCR(Tesseract, CLOVA OCR, Google Cloud Vision) / 이미지 읽는 LLM
- 날짜 형식·기간 선후 검증, 다른 값과 다르면 관리자 확인. 텍스트와 이미지 해시만 저장, 이미지는 게시 안 함

### 5.9 네이버·검색 API

- [확인 필요] 네이버 "전시 모아보기" 활용 방안 선택. 추천: 방안 1(사람이 보고 누락만 관리자 화면에 입력)으로 시작하고 방안 2(연결된 원래 예매처로 찾아감)·3(공식 검색 API) 추가. 방안 4(검색 화면 직접 수집)는 약관 확인 전 비추천
- 네이버 검색 API가 NAVER API HUB(네이버 클라우드)로 이관 중. 신규는 `naverapihub.apigw.ntruss.com/search/v1/news`, 헤더 `X-NCP-APIGW-API-KEY-ID`/`X-NCP-APIGW-API-KEY`
- 카카오 Daum 검색 API(`dapi.kakao.com/v2/search/blog`, `Authorization: KakaoAK …`), 카카오 로컬 API(장소 → 좌표)
- [확정] 검색 결과는 전시 데이터로 쓰지 않고 관리자 화면 "새 전시 후보"로 보여줌. 등록은 원래 출처에서 확인한 정보로
- 약관 확인 전에는 검색 결과를 DB에 쌓지 않음. API 키는 코드에 넣지 않음
- 쓰지 않음: Google Custom Search JSON API(신규 고객 받지 않음), Bing Search API(종료)

### 5.10 같은 전시 판별

- 실제 사례: NOL `스페인 미술 500년: ㅤ 빛과 어둠의 연대기 ㅤ` vs 예술의전당 `스페인 미술 500년: 빛과 어둠의 연대기`(보이지 않는 문자만 다름), 카카오 `★얼리버드★ 20세기 사진 거장전`, `수잔발라동` vs `수잔 발라동`. 반대로 `앤디 워홀 : 예술을 팔다 - 대구`는 순회전이라 다른 전시
- 1단계 같은 출처 안에서는 출처 고유 번호(NOL 상품 ID, 카카오 매장 ID, 예술의전당 `SN` 등)로 확정 → SourceLink
- 2단계 제목 정리: NFKC, 보이지 않는 문자(U+3164, U+2800, U+200B, 전각 공백) 제거, 판매 문구(`[얼리버드]`, `★얼리버드★`, `[가을 할인 50%]` 등) 제거, `展`→`전`, 전각→반각, 부제 구분 기호 통일, 지역 꼬리표 분리. 주제목·전체 제목 두 가지 비교 키
- 3단계 장소 묶기: VenueAlias, 전시실·층 표기 제거, 좌표 거리
- 4단계 같은 시·도 + 기간 겹침 후보만 비교. `pg_trgm` `similarity()`, 장소·날짜 일치로 점수 → 확실히 같음(자동 합침) / 애매함(관리자) / 확실히 다름(새 Event)
- 5단계 관리자 판정 저장, 다음 수집 때 다시 묻지 않음, 되돌리기 가능
- [확인 필요] 장소 거리 기준, 날짜 오차 허용 일수, 자동 합침 점수(사람이 판정한 샘플 수십 쌍으로 정함)
